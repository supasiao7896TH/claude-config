## 0 · ตัดสินใจก่อน 30 วินาที

| อาการ | ทำอะไร |
|---|---|
| หน้าขาว / กดอะไรไม่ได้เลย | rollback ทันที ไม่ต้องหาสาเหตุก่อน |
| ตัวเลขผิด / คำนวณผิด | **rollback ทันที** — เครื่องมือในโรงงานที่ให้ค่าผิด อันตรายกว่าเครื่องมือที่ล่ม |
| หน้าตาเพี้ยนแต่ใช้งานได้ | แก้ไปข้างหน้าได้ ไม่ต้อง rollback |
| ผู้ใช้บางคนเห็นของเก่า | ไม่ใช่ปัญหา deploy — ดูข้อ 3 (CACHE_NAME) |

## 1 · Cloudflare Workers — เร็วที่สุด ~30 วินาที ยังไม่ต้องยุ่งกับ git

```bash
npx wrangler deployments list
# หา entry ที่ "ดีล่าสุด" (ก่อนตัวที่พัง) แล้วจด Version(s) id ของมันไว้
# เช่น "Version(s):  (100%) 1a50d5ff-cf55-4d3c-b16f-4d137b1aed3b"
#                                └────────────── นี่คือ version-id ──────────────┘

npx wrangler rollback <version-id> -y -m "rollback: <อาการที่เจอ> <เวลา>"
# ⚠️ ต้องใส่ <version-id> ที่จดมาตรงๆ — ไม่ใส่แล้วปล่อยว่าง syntax ยังถูกต้อง (เป็น optional)
# แต่ไม่ได้ทดสอบพฤติกรรมตอนไม่ใส่ ระบุเสมอเพื่อความชัดเจนว่าจะย้อนไปตัวไหนแน่ๆ

npx wrangler deployments list
# ยืนยันว่า entry บนสุดตัวใหม่ล่าสุดชี้ Version(s) กลับไปที่ <version-id> เดิม 100%
# และ Message ตรงกับข้อความที่เพิ่งใส่ไป — นี่คือหลักฐานว่า rollback สำเร็จจริง
```

**ทำไมต้องระบุ `<version-id>` เอง ไม่ปล่อยให้ wrangler เดา:** `--help` บอกว่า `version-id`
เป็น positional แบบ optional (`wrangler rollback [version-id]`) แต่การซ้อมจริงทดสอบเฉพาะ
แบบระบุ id ตรงๆ เท่านั้น — ไม่รู้ว่าไม่ใส่แล้วจะย้อนไปตัวไหนแน่ ระบุเองชัดเจนกว่าปลอดภัยกว่าเสมอ

ถ้าอยากเลือกเวอร์ชันเจาะจงแบบ gradual rollout แทนการสลับทันที (ยังไม่ได้ทดสอบจริง —
ใช้ `wrangler versions deploy` ซึ่งเป็นคนละคำสั่งกับ `wrangler rollback`):

```bash
npx wrangler versions list
npx wrangler versions deploy <version-id>@100% -y
```

## 2 · ทำให้ git ตรงกับความจริง — ทำทันทีหลังข้อ 1

production ถูกย้อนแล้ว แต่ `main` ยังมีโค้ดที่พังอยู่ ถ้าไม่แก้ deploy ครั้งถัดไปจะพังซ้ำ

```bash
git revert --no-edit <sha-ที่พัง>
# แก้ CACHE_NAME ใน sw.js ให้เดินหน้า (v7 → v8) — ห้ามย้อนกลับเป็นค่าเดิม (ดูข้อ 3)
git push origin main
```

**ห้าม `git reset --hard` + force-push เด็ดขาด** — `sa-git-manager` ห้ามไว้ และจะทำให้
การ sync ระหว่างเครื่องบ้านกับเครื่อง office พัง

## 3 · `CACHE_NAME` ต้องเดินหน้า ไม่ใช่ถอยหลัง (จุดที่พลาดกันมากที่สุด)

ถ้า deploy ที่พังขึ้นไปแล้ว มือถือทุกเครื่องที่เปิดแอปกำลังถือ shell ที่พังอยู่
**ภายใต้ชื่อ cache ปัจจุบัน**

- คืนค่าเป็นชื่อเดิม → เครื่องเหล่านั้นยัง match cache ที่มีอยู่ → **ยังเห็นของพังต่อไป**
- ตั้งค่าใหม่ที่สูงกว่า → `activate` ลบ cache เก่าทิ้ง → ได้ของใหม่จริง

**rollback ที่ข้ามข้อนี้จะ "สำเร็จ" ในมุมของ deploy แต่ผู้ใช้ยังเห็นของพัง**

## 5 · ข้อมูลผู้ใช้ใน IndexedDB — จุดที่ย้อนไม่ได้

**migration เป็น forward-only ไม่มี down-migration** ถ้าเวอร์ชันที่พังได้ bump `DB_VERSION`
ไปแล้ว การย้อนโค้ดกลับ **ไม่ได้ย้อนโครงฐานข้อมูลในเครื่องผู้ใช้**

- เบราว์เซอร์จะ **ปฏิเสธ** การเปิด DB ด้วย version ที่ต่ำกว่าที่มีอยู่ → แอปเวอร์ชันเก่าเปิดไม่ขึ้น
- ทางแก้: **อย่า rollback โค้ดที่ bump DB_VERSION** ให้แก้ไปข้างหน้าแทน (bump อีกครั้ง
  แล้วเขียน migration ที่ถูกต้อง)
- ป้องกันล่วงหน้า: ก่อน deploy ที่มีการเปลี่ยน `DB_VERSION` ทุกครั้ง ต้องมีเทสต์ migration
  ที่พิสูจน์ว่าข้อมูลเดิมอยู่ครบ (`tests/unit/starter-contract.test.mjs` มีตัวอย่าง)

## 6 · หลัง rollback เสร็จ

```
[ ] เปิด URL จริงบนมือถือ ยืนยันว่าใช้งานได้แล้ว
[ ] เช็ค build stamp ในหน้า ว่าเป็นเวอร์ชันที่ตั้งใจย้อนไป
[ ] เปิด GitHub issue บันทึกว่าเกิดอะไร ทำไมเทสต์ไม่จับ
[ ] เพิ่มเทสต์ที่จะแดงถ้าบักนี้กลับมา — ไม่งั้นมันจะกลับมา
```

ข้อสุดท้ายสำคัญที่สุด · rollback ที่ไม่ตามด้วยเทสต์ คือการเลื่อนปัญหาออกไป ไม่ใช่การแก้

## 7 · ผลการซ้อมจริง (2026-09-02 · `condo-rental-app`)

ทำตามขั้นตอน 1-4 เดิมของหัวข้อนี้ครบ — บันทึกผลจริงไว้ที่นี่แทนคำแนะนำเชิงทฤษฎี

**สิ่งที่ทำ:** เปลี่ยน `<title>` เป็น "🔴 ROLLBACK DRILL TEST 🔴" (จุดเดียว ไม่แตะ logic/ข้อมูล)
push เข้า `main` จริง รอ deploy จริง ยืนยันว่าพังจริง แล้ว rollback กลับด้วยคำสั่งในข้อ 1

|---|---|---|
| 10:39:56 | push commit ที่ทำให้ title พัง | — |
| 10:40:46 | deploy จริงขึ้น production (ยืนยันจาก `Created:` ใน `deployments list`) | **50 วิ** |
| 10:41:04 | สั่ง rollback (`wrangler rollback 1a50d5ff... -y -m "..."`) | — |
| 10:41:27 | rollback สำเร็จ — `deployments list` ยืนยัน 100% ชี้กลับ version เดิม | **23 วิ** |
| 10:42:22 | `git revert` + push เข้า `main` (ทำ git ให้ตรงความจริง) | — |

**รวม: จากพังจริง (10:40:46) ถึงแก้จริง (10:41:27) = 41 วินาที**
**รวมทั้งกระบวนการ (จากกด push ครั้งแรกถึง rollback สำเร็จ) = 1 นาที 31 วินาที** — เป้า < 5 นาที ✅

**สิ่งที่เรียนรู้จากการซ้อมจริง (ไม่ใช่แค่ทฤษฎี):**

1. `wrangler rollback` ไม่ต้อง build ใหม่ — เป็น API call ล้วน จึงเร็วกว่า deploy ปกติมาก
   (23 วิ รวม `npm ci` และติดตั้ง wrangler ซ้ำ ตัวคำสั่ง rollback เองใช้แค่ ~2 วิ)
2. **runbook ฉบับร่างเดิมมีบั๊ก** — เขียนให้ "จดรหัสไว้" จาก `deployments list` แต่บรรทัดถัดไป
   ไม่ได้ใส่รหัสนั้นเข้าไปในคำสั่ง `rollback` เลย เพิ่งเจอตอนซ้อมจริง ไม่ใช่ตอนเขียนเอกสาร
   — เป็นตัวอย่างว่าทำไม "runbook ที่ไม่เคยซ้อม คือเอกสาร ไม่ใช่ความสามารถ"
3. deploy ทั้งหมดของแอปนี้รันผ่าน GitHub Actions ไม่ใช่ `wrangler` บนเครื่อง local เลย —
   แปลว่าซ้อม/สั่ง rollback จริงทำได้จาก Claude Code (บนเว็บหรือเครื่องไหนก็ได้ที่ push
   เข้า repo ได้) โดยไม่ต้องนั่งหน้าเครื่องที่มี `wrangler login` ไว้

**ซ้อมกับแอปอื่น** ให้ทำตามขั้นตอนเดียวกัน: (1) เลือกแอปที่ deploy จริงในเวลาที่ไม่มีคนใช้
(2) เปลี่ยนอะไรที่เห็นชัดแต่ปลอดภัย 100% เช่น `<title>` (3) จับเวลาทุกขั้น (4) เกิน 5 นาที
= runbook หรือ ops access ของแอปนั้นยังไม่พร้อม ต้องแก้ก่อนของจริงเกิดขึ้น
